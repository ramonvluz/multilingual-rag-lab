Execution objects

DOC-002#SEC-01

A published workflow is immutable and receives a revision such as FLW-ACCT-R17. Editing the draft does not affect the active revision until an authorized publisher promotes it. Each accepted event starts one run. The run retains the revision, input hash, workspace, and trigger metadata for audit purposes.

A step may be automatic, conditional, timed, or human. Automatic steps call a connector or transform data. Conditional steps select a route using typed fields. Timed steps pause until a timestamp. Human steps create review tasks and place the run in WAITING_REVIEW.

Trigger behavior

DOC-002#SEC-02

Webhook triggers acknowledge valid requests after schema and signature checks. Scheduled triggers use the workspace time zone. API triggers accept the Idempotency-Key header. The platform trims surrounding whitespace but does not change letter case in that key.

Since release 2.5, scheduled triggers use calendar-aware recurrence rules. An older interval schedule may drift around daylight-saving transitions; the current scheduler preserves the configured local wall-clock time.

Retries and terminal states

DOC-002#SEC-03

Connector steps retry only errors marked transient. The default policy is three attempts with delays of 30 seconds, 2 minutes, and 10 minutes. Error RL-4290 may include Retry-After, which overrides the next delay without increasing the maximum attempt count. Validation errors such as PX-1047 are permanent and do not retry automatically.

A run is terminal in SUCCEEDED, FAILED, or CANCELLED. A task deadline can move a run from WAITING_REVIEW to RUNNING through an explicit timeout route. It never silently approves a task.

Revision and rollback

DOC-002#SEC-04

Rollback activates an earlier published revision for new events. In-flight runs continue on the revision captured at creation. Operators should record the rollback in a change ticket and compare failure rate by revision. Connector credentials are workspace resources and are not rolled back with the workflow.

Audience and prerequisites

DOC-002#SEC-05

This document is for people who operate or administer OrbeFlow and already understand workspaces, environments, and platform identifiers. It assumes authorized access to the cited records; investigation never grants broader access by itself. Its specific focus is functional behavior, product objects, and module boundaries. Before acting, confirm production versus sandbox, active plan, region, and the revision or version shown by the evidence. The same display name may exist in several environments. A successful sandbox action must be reviewed again before production use. When a required role is unavailable, preserve evidence and route the case to the accountable owner instead of bypassing Access Gate controls.

Minimum evidence

DOC-002#SEC-06

Record UTC time, region, workspace, environment, relevant identifiers, and the observed result. For runs, combine event_id, RUN-, workflow_id, and revision. For tasks, include TSK- and state. For connections, include CON- and provider but never a secret. Copy codes such as PX-1047 or RL-4290 exactly. A screenshot may omit structured fields, so prefer a redacted export or machine-readable response. State when an identifier is missing rather than inventing it. Remove personal or commercial content that is not needed for diagnosis. The final record should allow another operator to reproduce the analysis without relying on the original investigator's memory.

Operational example

DOC-002#SEC-07

Consider a request about “Workflow execution model.” The operator first bounds the time and environment, locates the object by stable identifier, and compares expected with observed behavior. If they differ, the operator records one hypothesis and selects the lowest-risk check. A description without an exact code may resemble several articles, so object type and current state are decisive. If evidence points to another domain, transfer the case with its timeline intact. Repeating an operation with a new identifier before understanding idempotency can create external duplicates, hide the first failure, or make later reconciliation ambiguous.

Boundaries and exceptions

DOC-002#SEC-08

This document does not authorize a plan change, weaker security control, record deletion, or access to unredacted content. Confirm commercial values and operational limits in the current catalog even when historical release notes contain numbers. An exception needs a reason, expiration, owner, and risk-appropriate approval. Authentication, retention, and residency exceptions require Security Admin participation. Emergency approval may accelerate incident mitigation but still requires later review. If two current sources appear inconsistent, stop the action and open a documentation correction instead of selecting the more convenient value.

Validation and related documents

DOC-002#SEC-09

Finish by confirming that the expected result occurred and that another module was not harmed. For changes, compare a before and after window. For support, reproduce only when safe. For policy questions, confirm effective date and version. Useful related documents include DOC-001, DOC-012, DOC-016. A relationship supplies context, not automatic precedence. Current policy overrides an operational guide, the current catalog overrides historical release notes, and object evidence overrides assumptions based on display names. Record the section identifier used so later evaluation can distinguish the correct evidence from a passage that is merely semantically similar.
